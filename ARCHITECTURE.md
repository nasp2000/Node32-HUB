# Node32-HUB Architecture

## 1. Overview

Node32-HUB is a multi-protocol industrial communication hub targeting ESP32-S3 (Xtensa) and ESP32-P4 (RISC-V). It integrates:
- **Serial/parallel**: RS232 (UART + USB Serial, board-dependent routing), LPT/DB25 parallel port
- **Industrial protocols**: Modbus RTU (RS232/RS485), Modbus TCP (WiFi/Ethernet), Modbus slave
- **CNC**: GRBL-protocol G-code sender with streaming, real-time jogging, position monitoring
- **Fieldbus**: CAN bus via internal TWAI controller
- **Sensors**: AHT20 (temp/humidity), MQ135 (air quality), HX711 (load cell/scale), INA226 (current/voltage/power), MAX31865 (PT100/PT1000 RTD), BH1750 (lux), sound level, inductive proximity
- **Notifications**: SMTP email, Google Script email, customizable alerts with numeric thresholds
- **Multimedia**: camera (OV2640/OV3660, OV5647 on P4 MIPI; MJPEG streaming), internet radio (Shoutcast/Icecast), I2S audio (UDA1334A DAC + software MP3/FLAC/OGG/AAC/WAV decoders)
- **Web management**: full UI over WiFi AP/STA or Ethernet (W5500), real-time serial monitor, sensor charts, GRBL controller, radio UI, buffer viewer

Design principles: modules compile out at zero RAM cost when disabled (`#if ENABLE_X == 1`), PSRAM for large allocations (frame buffers, G-code files, sensor history), PROGMEM for all UI and i18n strings, no `new`/`malloc` in hot paths, atomic config writes, unified handler layer for WiFi and Ethernet.

## 3. Web UI Architecture (4-layer)

```
assets/ (PROGMEM) → renderers/ (streaming) → handlers_unified/ (HTTP) → routes/ (registration)
```

**Assets** (`src/webpages/assets/`) — `const char PAGE_X[] PROGMEM = R"rawliteral(...)rawliteral"`. No DOCTYPE, html, head, or body tags — these are injected by the shell renderer. HTML fallback text in English (JS applies translation via `_t()`). Each asset page includes a home button as first child of `.wrap`: `<div class='actions nav-inicio'><a href='/' class='btn' data-i18n='btnHome'>&#127968; Início</a></div>`.

**Renderers** (`src/webpages/renderers/`) — `streamPageShellStart()` emits DOCTYPE, `<meta viewport>`, core.css, theme colors, and opens the `.wrap` + `.content` divs. `streamAutoJsFooter()` emits auto.js providing `customAlert`, `customConfirm`, `disableBtn`, `showLoading`, `_t()` (i18n key lookup), `showSavedCard`, and `customAlert` for success/error feedback. All pages use the shell — legacy monitor pages were migrated from raw C++ streaming.

**Handlers** (`src/webpages/handlers_unified/`) — unified `handleFoo(HttpRequest&, HttpResponse&)` serving both WiFi (AsyncWebServer) and Ethernet (separate AsyncWebServer instance on W5500). No code duplication. Authentication via `ensureBasicAuth`. JSON responses via `HttpResponse::sendJson`. API responses use `d.success` / `d.fail` pattern — never `d.ok` or raw `alert()`.

**Routes** (`src/webpages/routes/`) — `registerApiRoute("GET", "/api/foo", handleFoo)` registers on both servers in one call. MAX_API_ROUTES = 256 (~186 used, ~70 free). Exceptions that bypass the registry: streaming endpoints (`AsyncResponseStream`, `beginChunkedResponse`), body accumulation (3rd callback in `server.on()`), chunked file downloads — these use `server.on()` with manual Ethernet dispatch in `ethernet_bootstrap_routes.h` + `ethernet_bootstrap_handlers.h`.

**i18n system** — Two complete PROGMEM JSON files (`lang_en_ui.h` / `lang_pt_ui.h`, ~150 KB EN + ~160 KB PT, 2850 keys each). Build-time validation (`validate_i18n.py`) extracts all keys from both files and fails the build if any EN key is missing in PT (or vice-versa). Extra PT keys produce a build warning (ignored at runtime). At runtime, `activeLangUiJson` pointer selects the full JSON for the active language — zero RAM cost for the inactive set, no merge, no runtime processing. Firmware-internal strings (log messages, status) use `lang_active.cpp` with `L(activeLang->field)` macro.

**JS coding rules**: no arrow functions (`function(x){}` for ESP32 browser compat), `KeyboardEvent` uses `.key` not `.keyCode`, save responses return `customAlert('✅ Configuração guardada!')` + `showSavedCard()`, errors return `customAlert('❌ Erro: ' + message)`, confirmation uses `customConfirm()` (never native `confirm()`).

**Local processing pages** — 6 pages with continuous JS/polling are exempt from session timeout: `/sensor-charts` (Chart.js + heartbeat), `/grbl-controller` (SSE EventSource), `/serial-monitor` (polling), `/camera` (smart polling), `/radio-ui` (polling), `/buffer-viewer` (polling). These open in `target='_blank'` from home and are tracked via `charts_exempt_sessions` in the access page.

Each pack defines:

Build-time validation (`packs/pack_validator.h`, tested by `test_pack_validator`) enforces:
- **Hardware conflicts**: Sniffer + RS232 (UART1), Sniffer + DB25 (UART1), Modbus RTU + DB25 (UART1)
- **Dependency rules**: USBIP → USB_HOST, MODBUS_RTU/TCP/SLAVE → MODBUS, RS232_CHARTS → RS232, PAGE_GOOGLE_SCRIPT → GOOGLE_EMAIL, PAGE_SDCARD → SDCARD

## 6. Config & Persistence

**Dual-storage architecture** separates boot-critical secrets from bulk configuration:
- **NVS** (ESP-IDF non-volatile storage) — boot-critical only: `cfg_wifi` (WiFi credentials), `cfg_saved_net` (known networks), `cfg_web_pwd`, `cfg_tlnt_pwd`, `cfg_ap_pwd`, `cfg_smtp_pwd`
- **LittleFS** (SPIFFS successor, file-based) — everything else via slot-based JSON files at `/config/<stem>.json`

**ConfigManager** coordinates both stores. It owns 18 core stems (plus sensor and touch7 stems), each with a fixed max byte budget (see `addPage()` calls in `loadFromLittleFS`).

| Stem | Max bytes |
|---|---|
| `core` | 10240 |
| `rs232`, `access` | 8192 |
| `recipients`, `schedule`, `modbus`, `system`, `usb_server`, `smtp_email`, `alerts`, `telnet`, `ethernet`, `sdcard`, `debug`, `access_point`, `wifi_hybrid`, `do`, `ftp` | 4096 |
| `sensor_*` (`config`, `mq135`, `hx711`, `ina226`, `sound`, `max31865`, `proximity`, `prox_counters`, `bh1750`), `touch7` | 4096 |

**Atomic write pattern** (applies to ALL config files — both ConfigManager slots and sensor configs):
1. Write to `.<stem>.json.tmp`
2. Verify bytes > 0
3. `LittleFS.remove()` the original file
4. `LittleFS.rename()` `.tmp` → original path

Never open the final path for write directly. `littlefsBegin()` is always called (mount is async — no `littlefsMounted()` check). `saveAllConfigs()` is dead code — use `configManager.markDirtyAndScheduleSave()` for batch writes or `save(true)` for immediate writes.

**Config registry** (`/config/pages.reg`): JSON array listing every stem + max_bytes, auto-updated after every successful save.

**Sensor config files** — independent managers, same atomic pattern, NOT managed by ConfigManager:
- `/config/sensor_config.json`, `sensor_mq135.json`, `sensor_hx711.json`, `sensor_ina226.json`, `sensor_sound.json`, `sensor_max31865.json`, `sensor_proximity.json`, `sensor_prox_counters.json`, `sensor_bh1750.json`, `touch7.json`

**Adding a new config section**: create a new stem: defaults in `initDefaults()` + backfill in `ensureAllFieldsExist()` + save via `saveSection(stem)` (save and load); files at `/config/<stem>.json`. New pages create dedicated endpoints (<4 KB) - never modify the frozen `/api/configs`.

### 6.1 Telemetry & chart persistence standard (all packs, present + future)

Every telemetry source behaves identically with and without SD card. New
sources/packs MUST follow these 6 rules (pack validation does not enforce them
yet — review checklist):

1. **Dual sink, identical paths** — SD when `sdcardShouldUseSD()`, else LittleFS
   at the SAME path (`chartHistoryOpen*WriterFS`, sensor `periodicFlushToSD`
   `useFlash`, proximity CSV `/oee/` mirror, `turno_data.txt` parity).
2. **Configured cadence** — persisted writes follow `getSdcardFlushInterval()`
   (`flashFbWindowMs()`: 10m/30m/60m, default 30m; sensors floor 5m), same rule
   as the CSV ticks. Never a fixed private interval.
3. **Always-on PSRAM ring, no configuration** — every 1-min (or faster) sample
   lands in a volatile ring immediately (`PsramCircularBuffer`, ~30 min tail);
   the persisted files are the durable record, the ring is the recent detail.
4. **Merged API serving** — `.chart` endpoints serve file history + ring tail in
   one stride budget (`chartHistoryReadRawPoints` + `chartMergePoints` +
   `chartHistoryServePointsJson`, `chart_ring_serve.h`), always minute-fresh on
   either backend, same JSON envelope.
5. **Cleanup-covered** — every LittleFS data root is listed in
   `flash_fallback_cleanup.h` (today: `/logs`, `/data_fallback`,
   `/sensor_history`, `/oee`, `/DEBUG`, dynamic `/<sys>/`); undated files are
   never deleted; 1 MB `/config` reserve always enforced before writing.
6. **Email reads both** — day-email senders resolve SD files and LittleFS
   mirrors transparently (`flashFbCollectEmailFiles`); nothing web-visible may
   be SD-only except the accepted exceptions below. `.chart` binaries NEVER
   ride emails in any pack (graphs/OEE charts only — enforced in all three
   attachment filters: SMTP, Google, flash-collect). One funnel
   (`startEmailDayAsync`) serves every day-email type; the same
   (folder, subject) is never started twice inside 3 min
   (`email_day_dedupe.h` — scheduler double-fires, journal races and API
   double-clicks are refused loudly, journal retries at 20 min pass through).

**Accepted exceptions (by design, documented — not gaps):** camera photo/video
(SD-only, size), GRBL gcode file ops (503 `sd_unavailable` without SD),
`LPT_COPIES` (SD-only), bulk RS232/LPT/Modbus trees differ by backend
(`/{sys}/{FONTE}_{data}/` rotated 1 MB on SD vs `/data_fallback/<sys>/`
flat 256 KB on flash — same content, rotation needs differ), blobs
(`.bin`/`.avi`/`.jpg`/`.gcode`) never touch LittleFS.

7. **FTP upload parity** — `SD:`/`PSRAM:`/`LFS:` prefixes select the backend;
   legacy bare paths (`FTP_FS_AUTO`) resolve to SD when `sdcardShouldUseSD()`,
   else merge **LittleFS mirrors + PSRAM hot tier (deduped)** so no-SD uploads
   cover what SD would hold. `/config` is never uploaded (any backend, any
   prefix — refused loudly at listing entry and inside both scans).

8. **LittleFS cross-task guard (`lfsMutex`, all packs)** — the LittleFS
   instance is not thread-safe: concurrent metadata ops (open/stat/mkdir/
   remove/rename/list) from the email/FTP tasks and the loop task corrupt dir
   traversal and panic (`emailQueueProc` → `esp_vfs_stat` → `lfs_stat_` →
   `IllegalInstruction`, live .24 2026-10-14). Same discipline as `sdMutex`
   (recursive; `littlefs_manager.h`): email/FTP hold it across metadata ops
   (released before bulk streaming — torn bytes beat panic and writers are
   ms-fast); loop writers (journal, sensor/OEE/bulk/chart flushes, T24, log
   flush, cleanup) take it with short timeout and SKIP on contention (data
   stays queued for the next window). Readers on the email path (chart APIs,
   SENSORDAY summary) also hold it. Interactive files-page ops are still
   best-effort (follow-up). The wait is sliced (200 ms) with
   `esp_task_wdt_reset()` between attempts, and the mutex is published
   race-free via an atomic CAS (`src/lfs_mutex_guard.h`, covered by
   `tests/native/test_lfs_mutex_guard.cpp`).

9. **A task whose stack lives in PSRAM must NEVER touch the internal flash**
   (LittleFS/NVS/OTA — anything reaching `esp_flash_*`). With
   `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` IDF enforces this the hard way:
   `spi_flash_disable_interrupts_caches_and_other_cpu()` opens with
   `assert(esp_task_stack_is_sane_cache_disabled())`, i.e. `esp_ptr_in_dram(sp)`
   — **false for an external stack** — so the first flash read/write from such
   a task panics (`assert → abort`; decoded with `addr2line` on the n16r8 ELF,
   live .24 2026-10-15). That panic was the real reason SENSORDAY emails never
   left the board: `emailQueueProc` had a 32 KB `MALLOC_CAP_SPIRAM` stack and
   the SD→LittleFS parity made it read the flash mirror (no SD). The email
   tasks now allocate their stacks **internal** (`MALLOC_CAP_INTERNAL` in
   `runtime_email.cpp`). Check this for every new task that logs to LittleFS,
   reads config or serves files. `lfsMutex` (rule 8) is still required — the
   filesystem itself is not thread-safe.

**Per-source status (2026-10-14):**

| Source | Persisted cadence | Identical paths | PSRAM ring | Merged API |
|---|---|---|---|---|
| environment sensors | configured (floor 5m) | yes (CSV + `.chart`) | 7 d ring | yes (union: file head + ring tail via `streamMergedWindow`) |

## 7. Memory Management

- **PSRAM** (external SPI RAM, up to 8 MB on N16R8): camera frame buffers (MJPEG streaming), G-code files (GRBL sender loads into PSRAM), sensor history arrays (Chart.js data points), large JSON responses, USB host transfer buffers
- **PROGMEM** (flash): all web UI HTML/JS/CSS strings (assets, translations), i18n JSON (~150 KB EN + ~160 KB PT, ~310 KB total), flash log strings (`F()` macro), UI-format strings in `lang_active.cpp`
- **`memoryPressurePanic()`**: called before critical large allocations; logs current heap state, calls `psramRealloc()` pressure relief on caches, triggers soft reboot if heap drops below emergency threshold
- **Module guards**: `#if ENABLE_X == 1` at top of every `.cpp` file excluding core (log, config, network) — disabled modules cost exactly zero RAM at runtime (no task, no queue, no buffer)
- **Stack allocation**: FreeRTOS task stacks sized per task (see table below); `uxTaskGetStackHighWaterMark()` checked in diagnostics paths.
- **Web response buffers**: chunked/streamed output via `AsyncResponseStream` to avoid large contiguous allocations; JSON responses use progressive `addKey` serialization

## 9. FreeRTOS Tasks

The firmware runs on ESP32-S3 (dual-core Xtensa) or ESP32-P4 (dual-core RISC-V). Tasks are pinned to specific cores. Core 0 handles I/O and interrupts; core 1 handles application logic and web server.

| Task | Core | Stack | Purpose |
|---|---|---|---|
| `loop()` (Arduino main) | 0 | 8 KB DRAM | RS232 serial processing, sensor polling round-robin, scheduler tick dispatch, email queue drain, Modbus RTU polling, watchdog feed |
| AsyncWebServer WiFi | 1 | 16 KB DRAM | AsyncHTTP request handling on WiFi interface |
| AsyncWebServer ETH | 1 | 16 KB DRAM | AsyncHTTP request handling on W5500 Ethernet interface |
| Camera MJPEG | 1 | 32 KB PSRAM | OV2640/OV3660 frame capture + MJPEG streaming over HTTP |
| USB Host | 0 | 4 KB DRAM | EHCI USB host enumeration, pipe management, data transfer callbacks |
| AHT20 polling | 0 | 3 KB DRAM | Periodic temperature/humidity read (if enabled) |
| MQ135 polling | 0 | 3 KB DRAM | Periodic air quality read + calibration (if enabled) |
| HX711 polling | 0 | 3 KB DRAM | Load cell read with tare + averaging (if enabled) |
| INA226 polling | 0 | 3 KB DRAM | Bus voltage/current/power read (if enabled) |
| Proximity monitor | 0 | 3 KB DRAM | Inductive sensor state machine + counter (if enabled) |
| GRBL streamer | 0 | 4 KB DRAM | G-code line-by-line send with XON/XOFF flow control, real-time command injection |
| Audio playback | 1 | 4 KB DRAM | DFPlayer/MAX98357 background playback queue (if enabled) |

All tasks created with `xTaskCreatePinnedToCore()`. Stack watermarks monitored via `uxTaskGetStackHighWaterMark()` and reported on the system status page. Tasks for disabled modules are never created — zero overhead.

**USB Host task notes (ESP32-P4)**: `usbHostBegin()` is called directly in `setup()` — no delays, no root port power cycle toggles. Regressions from added delays or power cycles broke working boards; the v1.06 baseline code is stable. ESP32-S3 does not support `usb_host_lib_set_root_port_power()` (returns `ESP_ERR_NOT_SUPPORTED`). GPIO20 glitch (~170 ms high at boot) can corrupt USB PHY state — hardware fix: 10 kΩ pull-down to GND.

## 10. Testing

**Native C++ unit tests** (host-compiled, zero hardware needed):

- Framework: doctest (header-only v2.5.0)
- 108 suites, ~1180 `TEST_CASE`s, ~4800 `CHECK`s
- Three strategies:

  | Strategy | When | Example |
  |---|---|---|
  | **Standalone reimpl** | Deep ESP32 deps (ArduinoJson) | `test_config_validator.cpp` — reimplements `isSafeConfigJsonKey()` in-file |
  | **Compile prod source** | Few deps, stubs cover them | `test_config_validator` compiles `ConfigValidator.cpp` with stub `Arduino.h` |
  | **Extract standalone header** | Function used in multiple places | `modbus_crc.h` — `modbusCrc16()` extracted from `modbus_core.cpp` |

- Adding a suite: create `tests/native/test_<name>.cpp`, register in `Makefile` (`TEST_SRCS` + build rule) and in `run_native_tests.py` (`TEST_BINS` list)
- Run: `python chatgpt/scripts/run_native_tests.py` (or `pio run -e n16r8`, includes test step)
- Skip: `SKIP_NATIVE_TESTS=1 pio run -e n16r8`
- Coverage: `python tests/native/coverage.py [--html]` (40.1% on `charset_conversion.cpp`)
- Tooling unavailable: warning printed, continues unless `FORCE_NATIVE_TESTS=1`
